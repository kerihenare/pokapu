# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status

Pokapu is an open-source platform (Apache 2.0, see `LICENSE.md`) to help volunteers organise and deliver events, with a focus on Burning Man regional burns. The repo is in its **pre-code scaffolding stage**: the stack is chosen but there is no application code, build, lint, or test tooling yet. The accepted stack, recorded in `04-engineering/decisions/`:

- TypeScript 7 (strict, ESM) on Node.js 26 LTS (`.node-version`, `engines`).
- TanStack Start with React, built with Vite, self-hosted as a plain Node server through Nitro. Host-specific adapters must stay optional.
- PostgreSQL 17+ (developed against 18), accessed through Drizzle ORM over node-postgres (`pg`). Migrations are SQL generated by drizzle-kit, then reviewed, hand-edited where needed and committed. Never use `drizzle-kit push` against shared or production databases.
- Oxlint (type-aware through `oxlint-tsgolint`, with the TypeScript, React, jsx-a11y and import rules) and oxfmt (pre-1.0, pinned exactly), configured once at the source root. TypeScript 7 drops legacy `tsconfig` options such as `baseUrl`, so don't use them.
- Vitest (Node for logic, Browser Mode for components) and Playwright with `@axe-core/playwright` (WCAG 2.2 A/AA) against a production build. Database tests use real PostgreSQL (Testcontainers locally), are set up from committed migrations, and run against PostgreSQL 17 and 18. Features that touch Organisation-owned data must include cross-Organisation isolation tests.
- GitHub Actions on pull requests and pushes to `main`: install with a frozen lockfile, format, lint, typecheck, test, check migrations, then E2E. Keep logic in package scripts, pin actions to a commit SHA, and keep token permissions read-only by default.
- pnpm workspaces (`pnpm-workspace.yaml`: `apps/*`, `libs/*`). pnpm is pinned through `packageManager`, so use Corepack, and link internal dependencies with `workspace:`.

`04-engineering/source/package.json` (`@pokapu/source`) has no scripts or dependencies. The only package so far is `libs/design-system` (`@pokapu/design-system`, an empty manifest). None of the tooling is installed or wired into scripts yet, so don't assume commands. The only working commands are setup, run from `04-engineering/source/`: `corepack enable`, then `pnpm install`. Docker (or a compatible runtime) will be needed for database tests. Releases and deployment are undecided. Update this file as tooling lands.

## Repository layout

The top-level directories are numbered by discipline and act as the project's living documentation:

- `01-organisation/`: why Pokapu exists (`purpose.md`) and its values (`values.md`, an interpretation of the 10 Principles of Burning Man). Product, design, and engineering decisions should be consistent with these.
- `02-product/decisions/`, `03-design/decisions/`, `04-engineering/decisions/`: decision records for each discipline. Product has two accepted records (see below), engineering has the stack records, and design is still empty (`.gitkeep` only). Record significant decisions here, in the relevant discipline's folder, rather than leaving them implicit in code. Stack choices, such as a framework, package manager, or monorepo tooling, belong in `04-engineering/decisions/`.
- `04-engineering/source/`: where application source code lives. Run package commands from this directory, not from the repo root.
- `03-design/brand-guidelines/`, `03-design/style-guide/`, and `03-design/wireframes/`: placeholders for design guidance. Each has a `README.md` describing its intended scope, but no content has been decided yet. `libs/design-system` is the code counterpart.
- `99-system/`: tools, templates, and documentation for running the repository itself. Its `decisions/` folder holds records about how the project is run and documented, such as `261109-recording-decisions.md`.

## Product constraints on architecture

Two accepted product decisions shape everything engineering builds. Their engineering counterparts haven't been recorded yet.

- **Multi-tenancy** (`02-product/decisions/261109-multi-tenancy-with-organisations.md`): one deployment hosts many tenants, called **Organisations**. Data is isolated per Organisation by default, and a person can belong to several. Every feature must be Organisation-scoped from the start; a cross-Organisation leak is a serious defect. The isolation strategy (shared schema, schema per tenant, etc.) is an open engineering decision.
- **Plugins** (`02-product/decisions/261109-plugin-system.md`): functionality can be added without changing the core. Plugins are installed, enabled and configured per Pokapu instance and shared by all Organisations on it; there is no per-Organisation plugin configuration. They must respect Organisation isolation and can be built by third parties. The plugin architecture (extension points, packaging, sandboxing, in-process or not) is an open engineering decision.

"Organisation" is overloaded: it means a tenant, and also Pokapu itself (`01-organisation/`). Be explicit about which one you mean.

## Claude configuration

- `.claude/agents/` defines role-based subagents. Each reads the purpose, values and relevant decision records first, follows the conventions below, and ends with a report:
  - `architect`: system-level design (tenant isolation, plugin architecture, data model) and engineering decision records. No application code.
  - `designer`: flows, wireframes, brand, style guide, accessibility and design-system direction in `03-design/`.
  - `engineer`: implements scoped work in `04-engineering/source/`; stops and reports if a needed decision is unrecorded.
  - `lead-engineer`: stack and tooling choices, engineering standards, code review; keeps this file and the source README current.
  - `product-manager`: problems, requirements, acceptance criteria and product decision records in `02-product/`.
  - `project-manager`: GitHub issues, sequencing, dependencies, triage labels and status. No product or technical decisions.
- `.claude/skills/` exists but is empty.

## Conventions

- Every new decision MUST be recorded in the relevant discipline's `decisions/` directory, never left implicit. Name the file `YYMMDD-slugified-title.md`, using the date the decision was made (e.g. `261109-recording-decisions.md`). Follow that record's structure: an H1 title, `**Date:**` (YYYY-MM-DD) and `**Status:**` bullets, then `## Context`, `## Decision`, and `## Consequences` sections.
- A record's status is `Proposed`, `Accepted`, `Rejected`, or `Superseded` (with a link to the replacing record, e.g. `Superseded by 270115-new-title.md`). You can edit a record in place to amend or clarify it. When a decision is reversed or replaced outright, write a new record and mark the old one `Superseded`.
- Use British/NZ English spelling in docs ("organisation", "licence"), matching the existing content.
- Each directory's `README.md` describes its contents and current status. Keep them up to date as decisions are made, especially the root `README.md`'s Project Status and Getting Started sections and `04-engineering/source/README.md` once tooling exists.
