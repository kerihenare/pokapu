# Drizzle ORM and SQL migrations

- **Date:** 2026-11-09
- **Status:** Accepted

## Context

Pokapu uses TypeScript on Node.js (`261109-typescript-on-node-js.md`) with PostgreSQL (`261109-postgresql-database.md`). It needs a data-access layer and a way to evolve the schema.

Requirements:

- **Organisation isolation.** The architect hasn't yet chosen the isolation strategy (`../../02-product/decisions/261109-multi-tenancy-with-organisations.md`). The data-access layer must support all the candidates, including the hardest case: PostgreSQL row-level security with a per-transaction session setting (for example `set_config('app.organisation_id', …, true)`), set at the start of each request's transaction.
- **Strict types.** Query results should be typed from the schema, without a separate code generation step that contributors can forget to run.
- **Safe upgrades for self-hosters.** Self-hosted instances upgrade between releases on their own schedule, so schema changes must be explicit, ordered and reviewable.
- **Approachability.** Volunteers who know SQL should be able to read and write queries without learning a heavy abstraction.

Alternatives considered:

- **Kysely**: a thin, type-safe query builder, but migrations are hand-written and nothing models RLS policies.
- **Prisma**: well known, but it needs a generate step, its RLS support relies on client extensions and raw SQL, and v8 was still a release candidate.
- **MikroORM**: its filters could add Organisation scoping automatically, but it's a heavier unit-of-work abstraction with a smaller community.

## Decision

- Pokapu uses **Drizzle ORM** for PostgreSQL data access, through the **node-postgres** (`pg`) driver.
- The schema is defined in TypeScript with Drizzle. If row-level security is adopted, its policies and roles are defined there too (`pgPolicy`, `pgRole`).
- Migrations are **SQL files generated by drizzle-kit** from schema changes, then reviewed, hand-edited where needed (for example data backfills or anything the generator can't express), and committed.
- Migrations are applied in order when Pokapu is deployed or upgraded. `drizzle-kit push`, which changes a database without a migration file, may only be used against throwaway local databases, never shared or production ones.
- Drizzle 1.0 is a release candidate at the time of writing. We start on the latest stable release (0.45) and upgrade to 1.0 once it's stable. Moving to 1.0 is an amendment to this record.
- The minimum supported PostgreSQL version is **17**, and we develop and test against **18**. This settles the open point in `261109-postgresql-database.md`.

## Consequences

- Queries read like SQL and are typed from the schema, with no generate step.
- RLS session settings can be applied with one transaction wrapper, so isolation can be enforced in the database as well as in code if the architect chooses RLS.
- Committed SQL migrations give self-hosters a readable, ordered upgrade path, and reviewers see exactly what changes in the database.
- Generated migrations must be reviewed like code. The generator can misread a rename as a drop and an add, which would lose data.
- The Organisation-scoping pattern built on Drizzle (for example a scoped transaction helper, and whether raw `db` access is restricted) still needs an engineering standard once the isolation strategy is decided.
- How plugins add their own tables and migrations is part of the plugin architecture, which the architect still has to design.
- Upgrading Drizzle from 0.x to 1.0 will need some migration work, because 1.0 includes breaking changes.
